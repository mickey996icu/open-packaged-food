# OPF ODbL 与开源许可使用者指南（面向第三方接入与商业应用）

**[English](ODbL-GUIDE.md) | [简体中文](ODbL-GUIDE.zh-CN.md)** · **[项目治理](../GOVERNANCE.zh-CN.md)** · **[技术规范](../spec/SPEC.md)**

OpenPackagedFood (`opf`) 希望健康软件、零售工具、科研机构、大模型助手与商业应用能够放心接入开放食品包装数据。本指南用直白语言说明各层协议在常见接入场景中的边界。

> **免责声明**：本文档仅供工程接入与开源许可理解参考，**不构成正式法律意见**；涉及具体商业产品或衍生库上线合规，请由贵方所在地执业律师审阅确认。

---

## 1. 一眼看清各部分的许可边界（REUSE 分层标注）

- **直接调静态 JSON 接口，或在闭源代码中使用 Schema / 词典 / 地区规则（`Apache-2.0`）**：
  - 通过 HTTP 请求读取 `opf-data` 发布的静态 JSON（`/v1/...`）不触发 `AGPL-3.0-or-later`。
  - 在商业 App 或闭源后端直接引入 [`spec/schema/`](../spec/schema)、[`dictionaries/`](../dictionaries)（营养素/INS 添加剂/致敏原关键词）、[`profiles/`](../profiles)（`CN`/`US`/`EU`/`JP` 法规规则）或 [`skills/opf`](../skills/opf)，均适用无传染性的 **`Apache-2.0`** 协议，无需开源自身业务代码。
- **修改并对外托管本工具链或网页代码（`AGPL-3.0-or-later` / `Apache-2.0` 入站）**：
  - 修改 `opf/`、`bin/` 或 `web/`（不含保留上游 `Apache-2.0` 的 `web/vendor/` ZXing 扫码库）并将其作为网络服务对外运行，必须依据 `AGPL-3.0-or-later` 公开**该修改后程序自身**的源码；独立运行的闭源业务服务仅通过标准 HTTP/JSON 与 OPF 通信，不受影响。
- **商品数据库（`opf-data`，`ODbL-1.0` / `DbCL-1.0`）与裁剪标签图（`opf-media`，`CC-BY-SA-4.0`）**：
  - 数据主体遵循 `ODbL-1.0`，标签裁剪图遵循 `CC-BY-SA-4.0`。

## 2. 常见接入场景与 ODbL 合规说明

### 场景 A：内部 `SKU ↔ GTIN` 映射与集合数据库规则（ODbL §4.5）
- **典型用法**：连锁商超、内部配料审查工具或健康打卡 App 的后端，将自家私有 `SKU` / 货号绑定到 OPF 的 `gtin:` 编号，或将未经改写的 OPF 独立表与自有独立业务表并列放在系统内部。
- **ODbL 边界**：
  1. **纯内部使用**：若未向公众对外提供服务或分发衍生数据库，通常不触发 ODbL 对外开源要求。
  2. **集合数据库规则（Collective Database，ODbL 第 4.5 条）**：按第 4.5 条的集合数据库规则，当外部业务表仅保存自有的 `SKU ↔ GTIN` 映射而不实质提取、合并改写 OPF 的内容去构造混合衍生数据库时，**通常不构成**必须将私有数据库一并按 ODbL 开放的衍生数据库（具体边界请以 ODbL 原文为准）。
- **明确边界**：因为 `opf-data` 接纳社区按 `ODbL-1.0` 贡献的数据，维护团队对社区贡献的数据**没有私下豁免权**；凡是真正融合 OPF 与其他数据源并对公众提供使用的衍生数据库，请依法履行 ODbL 义务（不要指望靠付费买“豁免”来绕开第 4 条）。

### 场景 B：对外产品与衍生数据库的公开义务（ODbL §4.4 与 §4.6）
- **署名义务（§4.3）**：在界面或文档中明确注明数据来源 OpenPackagedFood (`opf-data`) 并附 `ODbL-1.0` 链接。
- **用衍生数据库生成产品（Produced Work）时的提供义务（ODbL 第 4.6 条）**：接入方尤其需要注意第 4.6 条——当你基于**衍生数据库**生成并向公众展示/提供**成果物（Produced Work，例如消费端 App 界面、营养分析报告或衍生特征结果）**时，必须按 `ODbL-1.0` 向接收方**同时提供以下两项之一**：
  1. 完整的衍生数据库本身（机器可读形式）；**或**
  2. 机器可读的变更差异文件（alteration file / 改动所用的处理方法），使他人可据此复原该衍生数据库。
- **必须保留核验边界与上下界语义**：
  - 严禁把 `basis: "regulatory_upper_bound"`（`< 0.5g`、`<= 5mg` 等）当作精确的数学 `0` 展示或记账。
  - 当接口返回 `"resolution": "divergent"` 时，严禁取均值或静默替用户选第一条，应引导按 `disambiguation.tracks_guide[]` 对照手头实物选择具体 `edition_id`。
- **图片资源引用**：若需自行打包或二次分发 `opf-media` 裁剪 WebP 图片，须遵守 `CC-BY-SA-4.0` 署名与相同方式共享规则。

### 场景 C：致敏原排查与高风险消费场景
- 务必向终端用户显式展示 `evidence_level`（区分 `community_reported` 与实拍已核验 `verified` / 多人印证 `corroborated`）、`t_active`（最近有效包装年月），并在显著位置提示**“一切以手头实物包装实际印刷为准”**，不得将开放数据表述为医疗或绝对零过敏担保。
