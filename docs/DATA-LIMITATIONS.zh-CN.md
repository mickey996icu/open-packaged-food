# OpenPackagedFood 数据局限性与使用边界说明

**[English](DATA-LIMITATIONS.md) | [简体中文](DATA-LIMITATIONS.zh-CN.md)** · **[项目治理](../GOVERNANCE.zh-CN.md)** · **[ODbL 使用者指南](ODbL-GUIDE.zh-CN.md)** · **[技术规范](../spec/SPEC.md)**

本文件仅用于客观陈述 OpenPackagedFood（`opf-data`）公共数据集**是什么、不是什么**以及目前已知的数据局限。

> **独立定位声明**：
> 1. 本说明**不构成对开放数据许可（`ODbL-1.0`）的额外附加限制或合同条件**。
> 2. **OPF 数据不构成对产品安全性、准确性或是否适合特定人群的任何担保。**
> 3. **接入方自行负责其产品或服务对终端用户的提示义务与合规义务。** 以下展示建议仅供参考，不代表维护方替任何第三方产品设定安全标准。

---

## 1. 这套数据是什么、不是什么

1. **仅是包装印刷文字的抄录，不包含未标示的交叉接触或共线生产风险**：
   - `opf-data` 收录的信息来源于包装表面可见文字的转录或公开发布的官方食品成分表。
   - 数据库**没有**涵盖未印在包装上的生产线交叉污染、共线残留或供应链临时替代料风险，也**不进行**实验室理化检测或成分验证。
2. **有照片不代表转录结果经过了人工核对**：
   - 现有 `evidence_level` 字段仅反映“这条记录提交了什么形态的附件材料”，**绝不代表内容已经被人工核对或产品安全**：
     - `corroborated`：表示有 2 位以上提交者上传过标签照片（无法保证账号背后不是同一人，也无法证明有人将结构化数值与照片逐字段核对过）。
     - `verified`：表示有 1 份标签照片及文件哈希（无法证明照片中的文字、数值与 JSON 转录结果完全一致）。
     - `official_registry_imported`：表示数据来自官方公开信息。
     - `community_reported`：表示仅有文字报告，没有照片附件。
   - 仅当未来实装且记录存在由工具在盲录模式下产生的 `"transcription": "independent_match"` 字段时，才说明出现过一次独立的“转录文本/数值与照片内容一致”比对——即便如此，也仅代表录入与包装印刷一致，**不代表产品本身安全**。
3. **同一条码的产品，在不同工厂或不同时期，配方可能已变更**：
   - 同一 GTIN 条码下可能共存多个代工厂版本（`track`）或新旧迭代版本。
   - `t_active` 仅是对记录观测时间的客观汇总，**不代表商品当前仍在售或在保质期内**：
     - 当存在包装生产年月（`vintage_month`）时，`t_active` 取其中最大值，即**见过的最近包装生产月（此后配方可能已变更）**。
     - 当全部证据均未标注 `vintage_month` 时，`t_active` 取最早提交年月（`min reported_at`），即**最早报告于某年月**，证明该记录至迟在当时已存在。
4. **修约上界与多版本消歧语义**：
   - 依据食品标签法规标零的营养素（`basis: "regulatory_upper_bound"`）表示低于该法规允许标零的修约阈值（`< X`），并非数学意义上的绝对为零。
   - 当产品解析模式为 `"divergent"` 时，表示同条码下存在至少两个核心配方不同的活跃变体；汇总区间仅供参考对比，不能代表手头具体某一实物包装的含量。
5. **社区协作与 AI 识读存在出错可能**：
   - 尽管入库前有格式、配料文字无损还原与营养换算校验，数据及照片识读仍可能存在 OCR 误识或人工抄录笔误。

## 2. 给下游接入方与开发者的展示建议

为帮助终端用户理解数据边界并避免产生准确性误解，**建议**接入方在产品界面或对话输出中考虑采取以下做法（是否采用及具体合规设计由接入方自行决定并负责）：

- **建议以证据形态而非“可信度/核验结论”展示 `evidence_level`**：建议采用诸如“有 2 位以上提交者上传过标签照片”“有 1 份标签照片”“来自官方公开信息”“仅有文字报告，无照片”等客观描述，建议不要译为或标注为“已核验”“已验证”“已认证”。
- **建议精准区分 `t_active` 的两种来源语义**：当 `t_active_basis == "vintage_month"`（或证据中含 `vintage_month`）时，建议标注“见过的最近包装生产月：YYYY-MM（此后配方可能已变更）”；当 `t_active_basis == "earliest_reported_at"` 时，建议标注“最早报告于：YYYY-MM”。
- **建议原样保留 `<` 修约上界与 `divergent` 分版提示**：建议区分 `<` 上界与 `0`，并在多版本并存时引导用户对照实物生产厂、SC 编号或执行标准选定版本。
- **建议在面向消费者的界面或与过敏原/膳食相关的输出中显著提示**：**“一切以手头实物包装实际印刷为准。”**

## 3. 公开勘误、撤回（`retracted`）与优先级处理

OpenPackagedFood 依赖开放且可核对的勘误流程持续修正错漏：

- **公开勘误渠道**：任何人均可随时通过 [`opf-data` 数据勘误与生命周期变更表单](https://github.com/mickey996icu/opf-data/issues/new?template=data_errata.yml) 报告字段错误、同条码多厂拆轨（`retrack`），或直接发起修正 PR。
- **撤回隔离机制（`lifecycle.state = "retracted"`）**：对存在严重误录、来源存疑或明显误导风险的版本，维护团队会通过 `retracted` 状态标记将其从活跃版本列表（`active`）及默认 Compact API 正常解析结果中移除隔离，同时保留审计记录以说明变更原因。
- **高关注度错漏处理**：**涉及致敏原遗漏、误标或配料表漏录等与饮食风险相关的勘误报告将优先处理**（维护方不设定固定小时或天数的硬性响应时限承诺）。
